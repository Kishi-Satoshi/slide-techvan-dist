# 改善メモ（スキルを育てるための記録）

資料を渡したあと、作っている間に起きたことを短くまとめて管理者に送る。
送られたメモは、週に 1 回の自動改善でまとめて分析され、スキルの手順・ルール・描き方の改善に使われる。

## 1. 送るか聞く

AskUserQuestion で 1 問だけ聞く:
「このスキルの改善のため、今回の作成で気づいた点を管理者に送ってもよいですか？（顧客名・数字などは伏せ、送る前に中身をお見せします）」
- 選択肢: 「内容を見てから決める」/「今回は送らない」
- 「送らない」なら、ここで終わる。何度も聞かない。

## 2. メモを書く

下の形で書く。**事実だけ**を書き、推測で埋めない。該当がなければ「なし」。

```
## 概要
- 資料の種類: <提案書 / 報告・分析 / 社内報告 / 営業資料 / その他>
- 枚数: <n> 枚、使った型: <cover, summary, table, …>
- 結果: <うまくいった / 一部やり直した / うまくいかなかった>

## 壁打ち・構成案で直されたこと
- <利用者が構成案のどこを、なぜ直したか>

## 生成の「確認が必要な点」
- <警告の内容（固有の語は伏せる）と、どう直したか>

## 見た目の問題・修正の依頼
- <画像の確認や利用者の指摘で見つかった問題と、どう直したか。直せなかったものも>

## 利用者の感想・要望
- <利用者の言葉を、固有の情報を伏せて>

## スキルの側で直すとよさそうなこと
- <手順・ルール・型・描き方のどこを変えれば、今回の手戻りを防げたか>
```

### 必ず伏せるもの
顧客名・社名・人名・製品名・案件名・具体的な金額や件数・社外秘の内容。
「A社」「〇〇システム」「約 n 百万円」のように置き換える。
資料の中身そのもの（deck.json）は送らない。必要なら構造だけ（「表 8 行 × 5 列」など）を書く。

## 3. 見せて、了承を得てから送る

1. メモ全文を利用者に見せ、「この内容で送ってよいですか？」と確認する。直したいと言われたら直す。
2. 了承を得たら、Issue（題名 `[改善メモ] <資料の種類>`、本文はメモ全文）を、使える方法で作る。上から順に試す:
   1. GitHub のツール（MCP の issue 作成）が使えるなら、それでリポジトリ `kishi-satoshi/slide-techvan` に作る。
   2. `gh` が使えるなら、メモを `<資料名>.改善メモ.md` に保存して:
      ```
      gh issue create --repo kishi-satoshi/slide-techvan --title "[改善メモ] <資料の種類>" --body-file "<資料名>.改善メモ.md"
      ```
   3. どちらも使えない・失敗したときは、メモ全文をそのままコピーできる形で示し、
      https://github.com/kishi-satoshi/slide-techvan/issues/new?template=improvement-memo.md
      を開いて、題名を `[改善メモ] …`、本文にメモを貼って送ってもらう。
3. 送れたら、その旨を伝える（メモのファイルを作った場合は消してよいと伝える）。
