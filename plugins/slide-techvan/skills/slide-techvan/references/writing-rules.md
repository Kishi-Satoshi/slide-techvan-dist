# 書き方ルール

資料の書き方のルール。構成案を作るときと deck.json を書くときに守る。

## 1. 1スライド1メッセージ

- 1枚で伝えることは1つだけ。言いたいことが2つあれば2枚に分ける。
- そのメッセージを「見出し」に書く。本体（表・カード・数字）は見出しの根拠。
- 内容の形と関係なく、同じ型を 3 枚以上続けない（データを順に見せるグラフの連続などはよい）。

## 2. 見出しは結論を言い切る文にする

| よくない（ラベル・題名） | よい（結論） |
|---|---|
| 売上推移 | 売上は3期連続で増加、前年比 **12%増** |
| 課題 | 対応の遅れは「一次切り分け」に集中 |
| スケジュール | 11月に試行、2月に全社へ展開 |
| 問い合わせ対応の現状について | 問い合わせの 6 割が初回で解決せず、再問い合わせに |

- **言い切り・体言止めを中心にする。** 「〜します」「〜です」で終わる見出しを並べない。同じ語尾を 3 枚続けない。
  言い切るのは、事実と、利用者に確かめた内容。確かめていない推測は書かない（§7）。
  （リード文・本文の文体は §6 のとおり相手に合わせる。見出しだけを短く言い切る）
- 見出しだけを上から順に読んで、話が通るようにする。
- 目安 20〜30 文字、最大 36 文字。
- 数字があれば入れる。比較の相手（前年比・目標比など）も書く。
- 強調したい語は `**…**` で囲む（1枚に1〜2か所まで）。デザインの強調色（青）で表示される。
  見出し・リード文・表紙のタイトルと副題では、1 行に収まるとき、強調語の下に薄い青のマーカーが自動で付く。

## 3. リード文は1行

- 見出しの下に置く補足。範囲・前提・根拠を1文で（最大 80 文字）。
- 例: 「2025年10月〜2026年9月の問い合わせ 12,480 件を集計しました。」

## 4. 本文の分量

| 部品 | 目安 |
|---|---|
| 箇条書きの要点 | 1項目 40 文字以内、2〜6 項目 |
| 要点の補足（detail） | 90 文字以内 |
| カードの見出し | 24 文字以内 |
| カードの本文 | 3枚以下なら 110 文字、4枚以上なら 80 文字以内 |
| 数字の項目名 | 12 文字以内 |
| 数字の補足（note） | 40 文字以内 |
| まとめの一文（callout） | 60 文字以内 |
| 表 | 10 行・7 列以内。超えるときは分けるか要約する |

- **数は内容の重さで決める。** 根拠・カード・箇条書きの数は 2〜4 で、毎回 3 点にそろえない。
  重い点は厚く書き、軽い点は 1 行で済ませる。全ページが同じ項目数・同じ行数にならないようにする。
  減らすのは重複だけ。数をそろえるために内容を削って薄くしない。

このほかの型（summary・quote・faq・options など）の上限は slide-types.md の各型の説明にある。
上限を超えると、生成時に警告が出る。警告が出たら文を短くする（文字を小さくして詰め込まない）。

## 5. 数字の書き方

- 数字は半角。4桁以上は3桁ごとにカンマ（12,480）。
- 単位は数字の直後（12,480件、96分、21.5%）。kpi では value と unit に分ける。
- 比較を添える（前年比 +18.2%、目標 95% に対し 97%）。
- 出典・集計期間・定義は note（注記）に書く。

## 6. 相手に合わせた言葉づかい

deck.json の `"audience"` で切り替える。

| | 社内向け（internal） | 顧客向け（client） |
|---|---|---|
| 呼び方 | 部署名・チーム名 | 貴社／当社 |
| 流れ | 結論 → 根拠 → 次のアクション | 事実 → 分析 → 提言 |
| 文体 | です・ます。短く言い切る | です・ます。根拠を添え、断定しすぎない |
| 表紙 | 部署名・日付 | 「○○株式会社 様」・日付・当社の部署名 |

## 7. 避けること

- 絵文字、「！」の多用、「など」「いろいろ」のようなあいまいな言葉。
- 主語のない長い文。1文は 60 文字程度まで。
- 同じ内容の繰り返し（見出しと本文で同じことを言わない）。
- 文頭の接続詞の連発（「また」「さらに」「加えて」「そのため」「このように」）。大半は消しても意味が通る。
- 先送りと決まり文句（「詳細は別途」「今後検討してまいります」「ぜひご検討ください」）。誰が・何を・いつまでにを書く。
  決まっていなければ、推測した案を作る前に選択式で確かめてから書く（下の「推測は消さず、作る前に確かめる」）。
- 考え方の枠を見出しに出すこと（「Situation」「課題／解決」）。中身の言葉で書く。
- 「御社」（書き言葉では「貴社」）、誇張（「画期的」「革新的」）、補足をつなぐダッシュ（——）。
- 機械が書いたように見える言い回しの一覧と言い換えの例は `ai-smell-ja.md`。deck.json を書く前に目を通す。
  生成すると、そのうち確度の高い語と、見出しの語尾・列挙の数のそろいすぎが「文面の確認」として指摘される。
- 確かめていない推測を資料に書くこと。「（仮）」「仮説」などの印を付けて書くのもやめる（読み手には未完成に見える）。

### 推測は消さず、作る前に確かめる

- 事実（ユーザーから受け取ったもの・資料にあるもの）は、そのまま言い切る。素材の数字は書き換えない。
- 足りない中身は、推測で考えてよい（空欄や「未定」で薄くしない）。
  例: 原因の仮説、施策の案、期間・体制・費用の目安、期限・担当の案、効果の見込み。
- 推測は、資料に書く前に選択式で確かめる（SKILL.md「推測の確認」）。
- 確かめた内容は、印を付けずに普通の文で書く。見込みの数字も、利用者が選んだものなら「年 300 万円の削減を見込む」のように普通に書く。
- 「未定」にするのは、利用者が「決まっていない」と答えたときだけ。「資料に入れない」と答えた点は書かない。
- 次のアクション・進捗の各行には、担当（誰が）と期限（いつまでに）を必ず書く。空のまま作らない
  （担当が 1 つも無いと、担当の欄そのものが表示されない）。生成時に空の行があれば「文面の確認」で指摘される。

## 機密の扱い（CONFIDENTIAL マーク）

機密情報を含むページには、右上に CONFIDENTIAL のマークを付ける（deck.json の `confidential`）。
構成案の一覧に「機密」の列を入れて利用者に見せ、直してもらってから作る。迷ったら強い方にする。

| 区分 | 値 | マーク | 付けるページの例 |
|---|---|---|---|
| 厳秘 | `"strict"` | 赤地に白文字 | 金額・見積・単価・費用の内訳・契約条件、個人名や個人情報、未公開の業績や数値、セキュリティに関わる情報 |
| 社外秘 | `"internal"` | 赤枠の白地 | 顧客固有の課題・要件・体制（役割のみ）・提案内容・スケジュール、社内の内部情報 |
| なし | （書かない）／`"none"` | なし | 目次、公開済みの一般的な内容、会社紹介など |

- 資料の一番上に `"confidential"` を書くと、すべての本文ページの既定になる（ページごとの指定が優先。外すページは `"none"`）。
- 表紙は、表紙か資料全体に指定があるときだけマークが付く。章扉・最終ページには付かない。
